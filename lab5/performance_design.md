# Оптимизация производительности: кэширование и rate limiting

## 1. Анализ производительности

**Частые операции:**

- `GET /v1/hotels` — каталог отелей при открытии списка и при интеграциях
- `GET /v1/hotels/by-city?city=…` — типичный сценарий поиска перед бронированием

**Медленные части:**

- Чтение данных из бд при каждом запросе без кэша
- Повторяющиеся одни и те же выборки при высоком трафике с одних и тех же клиентских IP

**Ожидания по производительности**

- время ответа для закэшированных `GET` — порядка миллисекунд за счёт кэщирования
- ограничение злоупотреблений поиском по городу — не более 100 запросов в минуту с одного IP (окно 60 с)

## 2. Стратегия кэширования

**Что кэшируется:**

- тело ответа `GET /v1/hotels`, потому что отели часто читаются, но редко меняются
- тело ответа `GET /v1/hotels/by-city` для конкретного значения `city`, закроем частые повторы одного города

**Стратегия:**
- Cache-Aside — при чтении сначала проверяем кэш; при промахе данные читаем из бд, результат сохраняем в ту же модель данных, что и без кэша, и кладём в кэш
- ttl в 60 секунд
- Инвалидируем кэш при создании отеля через **`POST /v1/hotels`**, сбрысываем кэш всего списка отелей и кэш отелей по заданному городу

## 3. Rate limiting

**Где применяется:** 

- `GET /v1/hotels/by-city` — ручка с параметром поиска

**Алгоритм:** 
- Fixed Window Counter — для каждого ключа клиента (`by_city:<IP>`) ведётся счётчик внутри текущего временного окна длиной 60 секунд. При превышении лимита - отлуп 429 с too many requests
- лимит: 100 запросов в минуту на IP

## 4. Влияние и метрики

**Кэш:** 
- снижает число обращений к бд на горячих чтениях; эффективность можно оценивать по cache hit rate = попадания / (попадания + промахи), метрики в коде не подключались

**Rate limiting:** 
- защищает сервис от всплесков и скрейпинга, стабилизирует использование CPU и соединений к бд
